【标题自洽规则 — 让读者不点开就知道“这是谁的项目、做了什么”】

1. 标题必须点出核心主体：仓库名 / 项目名 / 组织名。仓库名优先写成 `owner/name` 或通行项目名；不要只写“某开源项目”。
2. 原标题已经清楚点出主体的：英文标题翻译成中文、中文标题保持原意，不要为改写而改写。
3. 原标题只是版本号 / 代号 / 没信息量的 teaser（如 "v2.1.159"、"Small is a feature"、"Day 1"、"重磅发布"）时，结合【来源】和正文把主体补进标题。例：原标题 "v2.1.159" + 来源 "Neovim Releases" → "Neovim v2.1.159 发布"。
4. 补主体只能用【来源】或正文里真实出现的名字。正文和来源都没点出具体项目时，用上位词（如“一个本地优先的笔记工具”）兜底，绝不凭“行业常识”编一个具体仓库名 / 版本 / star 数。
5. 原标题表达的【文章类型和核心动作】是硬边界：How / Why / Guide / Analysis / Review / Benchmark 这类解释、分析、教程或评测标题，中文标题必须保留这个类型；不能因为正文谈到一个已经存在的项目、产品或新版本，就改写成“发布 / 推出 / 开源”。只有原标题明确宣布了发布、开源、上线，中文标题才能使用对应动作。保留文章类型不等于删主体：仍须按第 1-4 条补全正文或来源明确给出的组织、项目、仓库名。
   例：原标题 "How we rebuilt our CLI in Rust" + 来源和正文明确是 Zed → "Zed 如何用 Rust 重写 CLI"，不能写成 "Zed 发布 Rust CLI"。
   例：原标题 "Benchmarking SQLite 3.50" → "SQLite 3.50 基准测试：读写下限与 WAL 变化"，不能写成 "SQLite 发布 3.50"。
6. 本条的动作和背景里的旧发布要分清：原文把发布写成过去的事（“上周发布了 v2”“Last week we launched…”），本条是在讲用法、做演示或再次推广时，标题写介绍、演示或讲解，把发布交代成此前的事；不能写成“推出 / 发布 / 开源”，否则读者会当成今天的新闻。只有原文明确某项能力是现在才开放或新增，才对那一项用对应动作。
   例：正文 "Last week we open-sourced the runtime. Here is how to self-host it" → "上周开源的运行时怎么自托管：部署步骤与限制"，不能写成 "项目开源运行时"。
7. 不用“重磅、炸裂、颠覆、神器、必看”等夸张词；不用问句；不堆叠冒号。
